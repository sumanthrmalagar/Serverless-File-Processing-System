7. Evidence notes and cautions

  • The 25 DynamoDB records are not 25 independent test scenarios. They are 10 COMPLETED and 15 FAILED records. The set includes two versions of sample.png, seven zero-byte folder-marker records, four initial acceptance records, six additional positive fixtures, and eight initial or additional negative records. The breakdown is in Table 9.2 of the case study.
  • The captured SQS envelope verifies the destination behavior for one intentionally injected infrastructure failure. It does not prove every failure mode, the exact retry timing, or the handling of the message after capture.
  • The SQS envelope references incoming/images.jpg. A COMPLETED record with the same file name also appears in the DynamoDB scan. The evidence does not establish whether the completion came from a replay, a new upload, or a retry after the configuration was restored, so the case study does not assert an order.
  • No access keys, secret keys, session tokens, or passwords appear in the supplied screenshots or in SQS.txt. The AWS account number and a source IP address appear in some source material. The IP address is redacted in the reproduced envelope. In the published site build, the account number is replaced with 000000000000 in every screenshot where it appeared: 13 locations across 9 figures. The original captures are unchanged and remain outside the published assets.
  • The workspace build/ directory contains botocore 1.43.113, while the verified function.zip contains botocore 1.43.112. The case study cites function.zip as the release artifact and records the stale directory as a packaging lesson.
  • The IAM role page is named sfps-lambda-scoped-policy, while the repository documentation names the role sfps-lambda-role. The case study records the difference rather than smoothing it over.
  • The architecture and sequence diagrams in Figures 4.1 and 4.2 are mine, drawn from the implemented code and the deployed configuration. They are not AWS Console screenshots.
